# P1b Spike 实测报告：fflate 0.8.3 分片解压的内存与取消行为

日期：2026-10-24 · 环境：Node v24.15.0（与 Chrome 同源 V8；浏览器内复测列入待实测清单）

## 方法

1. 机制实验（`tests/zip-spike.test.ts` + 独立脚本）：记录每次 `push()` 触发的 `ondata` 块尺寸、push 次数、中止延迟。
2. 精确峰值测量：`node --expose-gc` 独立进程，`global.gc()` 后以 `heapUsed + external` 基线采样峰值（共享进程的 vitest 内测量含未回收垃圾，仅作松上界断言）。

## 发现的定律（全部实测验证）

**定律 1：fflate 同步 `Inflate` 每次 `push()` 调用发射该次调用产生的全部输出。**
`maxChunk ≈ 分片尺寸 × 该分片的膨胀比`，上限为 DEFLATE 理论最大压缩比 ~1032:1。
实测（16MB 全零炸弹，压缩流 16KB，膨胀比 1024:1）：

| 分片                | maxChunk 实测                    | 分片×1032 理论 |
| ------------------- | -------------------------------- | -------------- |
| 512B                | 528,384 B（=512×1032，精确吻合） | 528,384 B      |
| 2KB                 | 2,100,120 B                      | 2,113,568 B    |
| 4KB                 | 4,089,700 B                      | 4,194,304 B    |
| 8KB                 | 8,192,800 B                      | 8,388,608 B    |
| 64KB（≥压缩流尺寸） | 16,777,216 B（整包单块）         | —              |

注意：当分片 ≥ 条目压缩流尺寸时（炸弹压缩流极小），整个压缩流被一次吞入，单块 = 全部膨胀量。

**定律 2：峰值内存（heapUsed+external）≈ 5 × maxChunk**（fflate 内部输出缓冲倍增 + 发射拷贝）。
`--expose-gc` 精确测量（预算 2MB 的 16MB 炸弹）：

| 分片 | maxChunk | 峰值实测 | 峰值/maxChunk |
| ---- | -------- | -------- | ------------- |
| 2KB  | 2.00MB   | 9.93MB   | 5.0×          |
| 4KB  | 3.99MB   | 19.95MB  | 5.0×          |
| 8KB  | 8.00MB   | 32.13MB  | 4.0×          |
| 64KB | 16.00MB  | 80.06MB  | 5.0×          |

**定律 3：峰值只随分片大小缩放，与炸弹总膨胀量无关。** 4KB 分片时，无论炸弹膨胀 16MB 还是 1GB，峰值恒 ≈20MB。

## 决策（基线 §4.2 分支判定：**分支 A 通过**）

- 默认 `inputChunk = 4KB`：峰值恒 ≈20MB（与炸弹大小无关），正常档案开销可忽略（10MB 压缩流 ≈ 2,500 次分片读取）。
- 预算检查位于 `ondata` 回调内（实际产出计数），超限即停止喂入后续分片并丢弃引用；实测中止延迟 < 1ms（同步流：当前 push 返回即止）。
- 保留的分片定律断言（`tests/zip-spike.test.ts`）：maxChunk ≤ 分片×1100；共享进程峰值 ≤ 预算 + 6×maxChunk + 8MB（松上界防灾难回归；精确数字以本报告为准）。

## 修正记录

- 基线 v1 假设"瞬态 ≈ 分片 × 1032"——实测系数为 **5×**（fflate 内部行为），已在基线 §4.2 更新。
- 基线 v1 默认分片 64KB → 在炸弹压缩流 < 64KB 时单块可达全膨胀量（实测 16MB 单块、80MB 峰值）；1GB 炸弹（压缩流 ~1MB）下 64KB 分片峰值可达 ~330MB。**已改为 4KB 默认**。
